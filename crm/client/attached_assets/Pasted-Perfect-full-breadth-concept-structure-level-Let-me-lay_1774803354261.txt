### 2. Environment / config setup

All env vars validated at boot — if one is missing the process refuses to start rather than failing silently at runtime.

```
server/config/env.ts
  └── Uses Zod to parse process.env
  └── Exports a typed config object used everywhere
  └── Never import process.env directly elsewhere in the codebase

Required vars:
  DATABASE_URL          Replit-managed PostgreSQL connection string
  REDIS_URL             Redis connection (Upstash or Replit add-on)
  API_KEY_SALT          Salt for bcrypt key hashing
  ENCRYPTION_KEY        32-byte hex key for AES-256 (SIN, secrets)
  BLOB_STORAGE_URL      Azure/S3 blob endpoint
  BLOB_STORAGE_KEY      Blob storage access key
  NODE_ENV              'development' | 'production' | 'test'
  PORT                  Default 3000

Optional / per-carrier:
  MANULIFE_BASE_URL
  CANADA_LIFE_BASE_URL
  IA_FINANCIAL_BASE_URL
  (credentials stored in DB secrets table, not env)
```

**Concept:** Config is validated once at startup and exported as a frozen object. Every service imports `config` not `process.env`. This means misconfiguration fails loudly at boot, not silently mid-request.

### 3. Authentication middleware

```
server/middleware/apiKeyAuth.ts

Concept:
  1. Extract Bearer token from Authorization header
  2. Hash the incoming token with bcrypt (same salt as stored hash)
  3. Look up api_keys table WHERE key_hash = hash AND deleted_at IS NULL
  4. Check expires_at if set
  5. Load the tenant record for that key
  6. Attach { tenantId, tenant, apiKeyId } to req.context
  7. Update api_keys.last_used_at asynchronously (fire-and-forget)
  8. Reject with 401 if any step fails — never leak which step

server/middleware/tenantContext.ts

Concept:
  Runs after apiKeyAuth
  Sets the Postgres session variable: SET LOCAL app.tenant_id = '...'
  This activates the Row Level Security policy on every table
  All subsequent Drizzle queries in this request are automatically scoped
  Never trust tenantId from the request body — always use req.context.tenantId
```

**Security rule:** The tenant isolation is enforced at two levels — RLS in the DB, and `req.context.tenantId` always overriding any tenant ID in the request payload. Belt and suspenders.

### 4. Zod validation layer

```
server/middleware/validate.ts

Concept:
  A factory function that returns an Express middleware
  Takes a Zod schema and a target ('body' | 'query' | 'params')
  Parses the target against the schema
  On success: attaches typed parsed data to req.validated
  On failure: calls next(new ValidationError(issues))
  Never throws — always passes to error handler

Usage in routes:
  router.post('/plans',
    validate(insertPlanSchema, 'body'),
    planController.create
  )

shared/validators/plans.ts

  insertPlanSchema       — from createInsertSchema(plans)
  updatePlanSchema       — Partial of insert, omitting immutable fields
  planQuerySchema        — query params: status, clientId, page, limit
  planIdParamSchema      — { id: z.string().uuid() }

Module validators follow same pattern:
  insertRetirementProfileSchema
  updateRetirementProfileSchema
  triggerSimulationSchema        — { scenario, simulationCount }
```

**Key discipline:** Validators live in `shared/validators/` not in routes. Routes import validators, not the other way around. This keeps validation reusable if you add a CLI, a worker, or a second transport later.

### 6. Calculation engine service

```
server/engine/

Concept:
  The engine directory is a pure computation zone
  No imports from server/ (no DB, no HTTP, no config)
  All functions are pure: same inputs always produce same outputs
  Fully unit-testable without a database connection

server/engine/monteCarlo.ts

  runMonteCarlo(params) → SimulationResult
    params:
      assumptions       PlanAssumptions record
      years             number
      initialState      module-specific state object
      yearlyStepFn      (state, draws) => state
      successConditionFn (state, year) => boolean
    
    internally:
      draws correlated returns via cholesky.ts each year
      draws longevity from mortality.ts
      runs N simulations (params.assumptions.simulationCount)
      collects success/failure + final state per simulation
      computes percentiles via fast-sort
    
    returns:
      successRate       0.0 – 1.0
      p10/p25/p50/p75/p90 of primary metric
      sensitivityData   one-at-a-time shifts
      medianFinalState  for module-specific outputs

server/engine/cholesky.ts

  buildCholeskyFactor(correlationMatrix) → L (lower triangular)
  drawCorrelatedReturns(L, means, stdDevs) → { equity, bond, inflation }
  
  Called once per simulation year
  Uses Box-Muller to generate independent normals
  Applies L · Z to correlate them
  Converts to log-normal for each asset class

server/engine/mortality.ts

  drawLifeExpectancy(age, sex, smoker) → deathAge
  
  Uses Statistics Canada Life Tables (2020–2022)
  Stored as lookup arrays, not DB queries
  Returns a random draw from the conditional survival distribution
  Used by retirement engine to determine plan horizon per simulation

server/engine/modules/retirement.ts

  buildRetirementStepFn(profile, assumptions) → yearlyStepFn
  
  Closure that captures the retirement profile
  Returns the step function runMonteCarlo expects
  Each year: grows accounts, applies contributions or withdrawals,
             runs RRIF optimizer, applies CPP/OAS, checks ruin

server/engine/modules/rrif.ts

  optimizeDrawdown(state, targetIncome, age) → withdrawalPlan
  
  Implements the three-step drawdown heuristic:
    1. mandatory RRIF minimum
    2. OAS clawback check
    3. fill gap: TFSA → non-reg → extra RRIF
  Returns: { rrif, tfsa, nonReg } withdrawal amounts + tax estimate

server/engine/reference/cppOas.ts

  getCppBenefit(estimatedMonthly, startAge, currentAge) → monthlyAmount
  getOasBenefit(startAge, currentAge, netIncome) → { gross, clawback, net }
  getCppBreakevenAge(startAge1, startAge2, estimatedMonthly) → age

server/engine/reference/taxBrackets.ts

  getMarginalRate(income, province, year) → rate
  getEffectiveTax(income, province, year) → taxAmount
  
  Reads from in-memory bracket arrays (seeded from DB at startup)
  Not a DB query on every calculation — loaded once at boot

server/engine/reference/probate.ts

  getProbateFee(province, estateValue) → fee
  
  Provincial schedules stored as step functions
  Returns 0 for Quebec (notarial system)
  Flags Alberta's cap correctly

server/engine/reference/cesg.ts

  calculateCesg(contribution, lifetimeReceived, subscriberIncome, childCount)
    → { basicCesg, additionalCesg, clb, totalGrant }
  
  Enforces lifetime limit ($7,200)
  Applies ACESG income thresholds
  Applies CLB eligibility rules
```

**Key rule:** Services in `server/services/` call the engine and then write results to the DB. The engine itself never touches the DB. This means you can run the entire calculation engine in a test without any database connection.

### 7. Carrier sync job (BullMQ)

```
server/jobs/queues.ts

  Two queues:
    carrierSyncQueue    — processes carrier file fetch requests
    recalcQueue         — processes plan recalculations from stale flags

  Both backed by Redis
  carrierSyncQueue: concurrency 5, exponential backoff on failure
  recalcQueue: concurrency 3 (CPU-heavier), lower priority

server/jobs/carrierSyncJob.ts

  Job payload: { requestId, tenantId, clientId, carrierSlug, fileTypes }

  Step 1 — Load credentials
    Fetch tenant_carrier_credentials for this tenant + carrier
    Resolve secret from secrets manager using secret_ref

  Step 2 — Call carrier adapter
    adapters/index.ts registry maps carrierSlug → adapter class
    adapter.getClientFiles(advisorCode, clientId, fileTypes)
    Returns: raw carrier payload

  Step 3 — Parse and normalise
    Each adapter implements its own parser
    Outputs: { policies: PolicyRecord[], holdings: HoldingRecord[] }

  Step 4 — Upsert to DB
    Soft-delete old policies/holdings for this client + carrier
    Insert new records
    Update carrier_file_requests.status = 'complete'
    Store raw file in blob storage, set signed URL

  Step 5 — Flag stale plans
    Find all active plans for this client
    Insert plan_stale_flags rows for affected modules
    Enqueue recalcJob for each stale plan

  Step 6 — Send webhook (if registered)
    POST to tenant's registered webhook URL
    Payload: { requestId, clientId, status, modulesAffected }

  On failure:
    Update carrier_file_requests.status = 'failed', set error_message
    BullMQ retries up to 3 times with exponential backoff

server/jobs/recalcJob.ts

  Job payload: { planId, tenantId, modules: string[] }

  Step 1 — Load plan + assumptions
    Fetch plan with all module profiles and all three assumption scenarios

  Step 2 — Load reference data
    Tax brackets and benefit rates already in memory (loaded at boot)

  Step 3 — Run engine per module per scenario
    for each module in modules:
      for each scenario in ['base', 'optimistic', 'stress']:
        load module profile from DB
        call engine module's buildStepFn
        call runMonteCarlo
        upsert simulation_results row (ON CONFLICT DO UPDATE)

  Step 4 — Resolve stale flags
    Mark plan_stale_flags.resolved_at = NOW() for affected modules

  Step 5 — Generate action items
    Compare results against thresholds
    Insert/update plan_action_items:
      successRate < 0.75 → 'critical' retirement action item
      insuranceGap > 0   → 'high' insurance action item
      respShortfall > 0  → 'medium' resp action item
      policiesNamingEstate > 0 → 'critical' estate action item

server/jobs/adapters/index.ts

  Registry pattern:
    const adapters: Record<string, ICarrierAdapter> = {
      'manulife':     new ManulifeAdapter(config),
      'canada-life':  new CanadaLifeAdapter(config),
      'ia-financial': new IaFinancialAdapter(config),
    }
    export function getAdapter(slug: string): ICarrierAdapter

  ICarrierAdapter interface:
    getClientFiles(advisorCode, clientId, fileTypes) → Promise<RawCarrierPayload>
    parseFiles(payload) → { policies, holdings }
    healthCheck() → Promise<boolean>

server/jobs/adapters/manulife.ts

  Implements ICarrierAdapter
  Auth: OAuth2 client credentials flow, token cached in Redis with TTL
  Transport: REST API
  Parser: maps Manulife-specific field names to normalised schema
  Handles pagination if carrier returns multiple pages
```

### 8. Error handling pattern

```
server/lib/errors.ts

  Typed error class hierarchy:
    AppError (base)
      ├── ValidationError    (400) — Zod failures
      ├── AuthError          (401) — bad/missing API key
      ├── ForbiddenError     (403) — valid key, wrong tenant
      ├── NotFoundError      (404) — resource doesn't exist or soft-deleted
      ├── ConflictError      (409) — unique constraint violations
      ├── CarrierError       (502) — carrier API returned error
      └── InternalError      (500) — unexpected failures

  Each has:
    statusCode    HTTP status
    code          machine-readable string ('PLAN_NOT_FOUND')
    message       human-readable string
    details?      Zod issues, carrier error payload, etc.

server/middleware/errorHandler.ts

  Global Express error handler (4-argument middleware)
  
  If error is AppError:
    log at appropriate level (warn for 4xx, error for 5xx)
    return { error: { code, message, details }, meta: { requestId } }
  
  If error is unknown:
    wrap in InternalError
    log full stack with requestId
    never leak stack trace to client in production

  Async route errors:
    All route handlers wrapped in asyncHandler(fn)
    Catches promise rejections and calls next(error)
    No try/catch boilerplate in every route handler

server/lib/logger.ts

  Pino-based structured logger
  Every log entry includes: { tenantId, requestId, level, msg, timestamp }
  requestId generated at middleware entry, attached to req.context
  In production: JSON output (Replit log drain)
  In development: pino-pretty for readable output
  Never log: API keys, SIN, encryption keys, signed URLs
```

### How it all flows together

A complete request lifecycle — advisor triggers a plan recalculation:

```
POST /api/v1/plans/:planId/simulate

1. apiKeyAuth          → resolves tenantId, attaches to req.context
2. tenantContext        → sets RLS session variable in DB connection
3. rateLimiter         → checks per-tenant request budget
4. requestLogger       → logs inbound with requestId
5. validate(schema)    → parses body, attaches req.validated
6. planRouter          → matched to simulationController.trigger
7. planService         → verifies advisor owns this plan (tenantId + advisorId check)
8. staleFlagService    → marks all modules stale
9. recalcQueue.add()   → enqueues recalcJob, returns jobId immediately
10. Response: 202 Accepted { data: { jobId }, meta: { requestId } }

Meanwhile, in the worker process:
11. recalcJob picks up from queue
12. Loads plan + assumptions from DB
13. For each module × scenario: calls engine → writes simulation_results
14. Resolves stale flags
15. Generates action items
16. If tenant has webhook registered: POSTs completion event

Advisor polls: GET /api/v1/plans/:planId/results
→ Returns simulation_results for all modules + action items
```
