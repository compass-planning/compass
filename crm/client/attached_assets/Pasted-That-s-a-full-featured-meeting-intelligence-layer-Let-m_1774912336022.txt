That's a full-featured meeting intelligence layer. Let me design the complete architecture.---

### Platform integrations

**Microsoft Teams** is the most complex of the three. You invite a bot into the meeting using the Microsoft Teams Bot Framework — the bot joins as a participant, receives the audio stream via the Teams calling API, and can also trigger Teams\u2019 native recording via the Graph API (which drops an MP4 into the organiser\u2019s OneDrive). The simpler path for phase 1 is to use the Graph API recording rather than streaming audio: when a meeting ends, a webhook fires, you fetch the recording from OneDrive via Graph, download it, and hand it off to transcription. This avoids real-time streaming complexity and works with standard Teams licenses.

For the bot invitation flow specifically: the advisor clicks \u201cInvite bot\u201d in your CRM, your backend calls the Graph API to add the bot as a meeting participant using the meeting\u2019s join URL. The bot joins, signals it\u2019s recording, and the advisor gets a visual indicator in Teams that the session is being captured.

**Zoom** is cleaner. You register a Zoom OAuth app, request cloud recording permissions, and subscribe to the `recording.completed` webhook. When a meeting ends, Zoom sends a webhook with the recording download URL. You fetch the MP4/M4A, store it in blob storage, and enqueue transcription. No bot required \u2014 Zoom\u2019s cloud recording handles capture natively.

**In-app recording** uses the browser\u2019s MediaStream API. The advisor clicks Record, you capture `getUserMedia({ audio: true, video: false })` (or both for video), feed it into a `MediaRecorder`, and chunk the data to your server via WebSocket or chunked HTTP upload as the meeting progresses. On stop, you assemble the chunks into a WAV/WebM file and hand it to transcription. This works for any call the advisor takes \u2014 phone, Teams desktop, anything \u2014 as long as they\u2019re on your CRM at the time.

### Transcription engine

**Azure AI Speech** is the right choice for a Canadian-market product. It supports both English and Canadian French, has strong speaker diarization (labelling who said what), runs in Azure Canada Central (data residency satisfied), and integrates naturally with blob storage. You submit a batch transcription job pointing at your blob URL and poll for completion \u2014 typical turnaround is 0.5\u00D7 to 1\u00D7 real time.

**OpenAI Whisper** (self-hosted or via API) is a strong alternative if you want to avoid Azure lock-in, but speaker diarization requires an additional library (pyannote.audio) and Canadian French accuracy is slightly lower.

The transcript output you want to store is a structured JSON array \u2014 not a flat string:

```json
[
  { "speaker": "Advisor", "start": 0.0, "end": 4.2,
    "text": "So let\u2019s talk about your retirement timeline." },
  { "speaker": "Client", "start": 4.5, "end": 9.1,
    "text": "I\u2019m thinking 62, maybe earlier if the portfolio does well." }
]
```

Speaker labels come from diarization. You map \u201cSpeaker 1\u201d / \u201cSpeaker 2\u201d to advisor / client based on who scheduled the meeting in your CRM.

### AI processing pipeline

This is where the real value is created. Post-transcription, you run a single structured Claude API call per meeting with the full transcript, asking for all six outputs in one pass as structured JSON. One call is cheaper and faster than six separate calls, and it allows the model to reason about the meeting holistically \u2014 the compliance notes and plan triggers are more accurate when the model has seen the full context before generating any output.

**The six outputs:**

**Meeting summary** \u2014 a structured summary with four sections: what was discussed, key decisions made, client\u2019s stated goals and concerns, and advisor\u2019s recommendations. Not a bullet-point dump \u2014 a coherent narrative the advisor can read in 60 seconds and attach to the client file.

**Action items** \u2014 extracted as structured objects with owner (advisor vs client), description, and suggested due date inferred from any deadlines mentioned in the conversation. Items are written to the `meeting_tasks` table and can be promoted to the CRM\u2019s task system.

**Follow-up email draft** \u2014 a complete email from advisor to client recapping the meeting, confirming next steps, and listing any documents the client needs to provide. The advisor reviews and sends directly from the CRM. Tone should match the advisor\u2019s communication style \u2014 you can fine-tune this by including a brief style prompt derived from past sent emails.

**Compliance notes** \u2014 this is the highest-stakes output. The model extracts: KYC updates mentioned (change in employment, income, family status, risk tolerance), suitability-relevant statements (client expressed concern about volatility, client confirmed long time horizon), any advice given, and any client instructions received. These notes are stored separately with a `compliance_reviewed` flag \u2014 the advisor must explicitly sign off before the meeting is marked complete. This creates a defensible audit trail.

**Plan triggers** \u2014 the model listens for statements that should update the financial plan: \u201cWe\u2019re expecting a baby\u201d (RESP trigger), \u201cI\u2019m thinking of retiring at 60\u201d (retirement age change), \u201cWe just paid off the mortgage\u201d (debt module update), \u201cMy mother passed away\u201d (estate / inheritance trigger). Each detected trigger creates a `plan_stale_flag` entry and an action item prompting the advisor to update the relevant plan section.

**Advisor coaching** \u2014 private to the advisor only, never shown to the client. The model scores the meeting on: did the advisor discover the client\u2019s full financial picture, were needs-based questions asked, were any obvious planning gaps surfaced, was the conversation client-led or advisor-led. Delivered as a brief private note with 2\u20133 specific observations. Over time this builds a coaching history per advisor.

### BullMQ job additions

Two new queues slot into the existing job infrastructure:

**`meetingProcessingQueue`** handles the post-meeting pipeline. Job payload is `{ meetingId, tenantId }`. Steps: download recording from blob \u2192 submit to Azure Speech transcription \u2192 poll until complete \u2192 store transcript \u2192 run Claude AI pipeline \u2192 write `meeting_outputs` \u2192 create `meeting_tasks` \u2192 fire any `plan_stale_flags` \u2192 notify advisor via webhook/push.

**`transcriptionPollQueue`** is a delayed job that polls Azure Speech for completion every 60 seconds. When complete, it hands off to the AI pipeline step. This avoids blocking the main processing worker while waiting for transcription.

### Compliance and consent considerations

Recording consent is non-negotiable under PIPEDA and provincial privacy laws. The required flow:

Before the meeting starts, your CRM sends the client a pre-meeting email stating the session will be recorded and summarized by AI, with an opt-out link. The recording only begins if the client has not opted out. For Teams and Zoom, the platform\u2019s native recording notice (displayed to all participants) also satisfies the notification requirement but you should retain the pre-meeting email as documentary evidence.

The `compliance_notes` output and the `compliance_reviewed` flag create a two-step process: AI extracts the notes, advisor reviews and signs off. The advisor\u2019s sign-off is timestamped and stored. This mirrors how most E&O-conscious advisory firms handle meeting documentation today, just automated.
